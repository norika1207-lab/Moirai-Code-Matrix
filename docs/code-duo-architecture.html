Code-Duo 系統架構

一個本機的多視窗 AI 開發控制台。四個視窗各自驅動一個獨立的 Claude / Codex CLI 程序,由瀏覽器統一派工。

/Volumes/ADATA/dev/duo  ·  本文所有指令列、路徑、數字皆為 2026-07-15 於實機讀取原始碼與量測所得

它是什麼

兩個原廠 CLI(claude / codex)的程序編排器。用 subprocess 起它們、讀它們的 stdout、把輸出畫到瀏覽器上。

它不做什麼

不含任何推論邏輯、不改寫模型輸出、不持有 API key、不接觸憑證。它對「對話內容」是純傳遞。

誰是權威

資料的 source of truth 是兩個 CLI 自己的 session 檔。Code-Duo 只存 795 bytes 的指標。

給架構師的三句話: ① 它是 CLI 的殼,不是桌面 app 的殼,也不是 API client。 ② 一個視窗 = 一個 作業系統程序,四窗 = 四個彼此隔離的程序與 session。 ③ 你在畫面上看到的每一個字,都能在 claude CLI 自己寫的 jsonl 裡逐字對照。

02程序模型

這是本系統唯一真正「重」的部分。一次送出,可能同時起四個作業系統程序。

一次送出的展開

1 個 HTTP 請求 → handle_stream → N 個 threading.Thread(N = 目標視窗數,1 或 4)→ 每條 thread 起 1 個 subprocess.Popen → 逐行讀該程序 stdout → 全部 thread join() 後才收尾。

生命週期歸屬

程序 handle 存在 RUNNING[pane],供 Stop / ESC 呼叫 terminate()。 同時 PID 會寫進 duo_children.json;server 下次啟動時 _reap_orphans() 會把上一輪殘留的子程序收掉(收之前先驗 cmdline 仍是 claude/codex,避免 PID 重用誤殺)。

四個視窗之間,共享什麼、不共享什麼

項目共享?說明
作業系統程序不共享每窗自己一個 claude -p / codex exec,各自的記憶體與生命週期
對話 session不共享每窗 STATE[pane]["id"] 各自一條,各自 --resume 自己的
共享內容共享四窗讀同一份共享池:每輪的指令與產出自動進池,其他視窗下次跑時自動補上差額。見 §07
模型與推理強度不共享每窗 AGENT_CFG[pane] 獨立,可以一窗 Opus 一窗 Fable
引擎不共享可各自切 claude / codex
工作目錄 cwd不共享每窗獨立,決定 CLI 在哪裡執行、session 落在哪個 projects 目錄
HTTP server 程序共享同一個 python 程序,以 thread 服務;狀態變更用一把 LOCK 保護
登入態 / 訂閱額度共享四窗用的是同一個帳號的 CLI 登入態,額度是同一份

04一道指令的完整路徑

從鍵盤到畫面,經過的每一手。

  1. 你在底部打字並選目標

    目標四選一或 All。可拖檔案(上傳到專案下的 .duo_uploads/,回傳相對路徑)。

  2. 前端 send() 組出最終字串

    只做兩件事:解析開頭的 @視窗名 覆蓋目標;把附件路徑接到文字最前面(Claude 窗轉成 @檔名 引用格式)。內容本身一個字都不改。

  3. POST /api/stream {target, text}

    回應標頭 Content-Type: application/x-ndjson,連線不關,邊跑邊吐。

  4. handle_stream 分岔

    先對專案目錄拍一次磁碟快照(供第 8 步比對)。決定 panes = [target] 或全部四個。每個 pane 開一條 thread。

  5. 帶入共享內容

    把其他視窗做過、而這個視窗還沒讀過的部分,接到指令前面(見 §07)。有帶入時,畫面上會標一行 🔗 已帶入共享內容。沒有新東西就不帶。

  6. 起 CLI 子程序

    依該窗自己的 engine / model / effort / mode / cwd / session id 組指令列(見 §03),Popen 起來,handle 記進 RUNNING[pane],PID 記進 duo_children.json。

  7. 逐行讀 stdout,翻譯成前端事件

    CLI 每吐一行 JSON,server 就解析、映射(見 §05)、立刻寫進那條長連線。這是唯一的資料來源。

  8. 瀏覽器渲染

    文字進 markdown、工具進可折疊列、subagent 進狀態列、token 進計時行。

  9. 本輪的指令與產出進共享池

    這個視窗剛剛做的事,現在成為其他三個視窗下次跑時會讀到的內容。

  10. 收尾與磁碟比對

    所有 thread join() 後,再拍一次快照,_diff 出「這一輪磁碟上真的變了哪些檔」,交給 record_behavior 與 AI 的宣稱比對(見 §09)。

06Session 模型與 source of truth

這一節回答:對話存在哪、誰寫的、桌面 app 看不看得到、Duo 死了資料還在不在。

Code-Duo 不擁有任何對話資料。 它從來沒有寫過一個位元組進 session 檔。寫檔的是 claude / codex 這兩支原廠 CLI,寫的是它們自己的目錄。 Code-Duo 只記「哪個視窗現在指著哪個 session id」。

對話真身(CLI 擁有,5.9 GB 級)

Claude:~/.claude/projects/<cwd 編碼>/<uuid>.jsonl
編碼規則是把 cwd 的斜線換成減號:
/Volumes/ADATA/dev/duo → -Volumes-ADATA-dev-duo

Codex:~/.codex/sessions/**/*.jsonl,無 cwd 分目錄,session id 取自檔名中的 UUID。

Duo 自己的家當(KB 級)

duo_state.json · 哪個窗指著哪個 id + engine + cwd + model/effort + 共享池
memory.md · 共享記憶,人可讀的 markdown(見 §07)
duo_overrides.json · 17.8 KB · 你改過的 session 名字(不動原始檔)
duo_claude_groups.json · 1.8 KB · 群組名
duo_children.json · 2 B · 子程序 PID

07共享內容:四個視窗讀同一份

四個視窗在「對話 session」上彼此獨立,但在「知道發生了什麼」這件事上,讀的是同一份共享內容。這是預設行為,不是開關。

規則:每個視窗每完成一輪,它的指令與產出就進入共享池。 任何視窗要跑之前,系統會把其他視窗做過、而它還沒看過的部分自動帶進它的輸入。 沒被呼叫的視窗不需要做任何事,下次輪到它時,它自然就是最新的。

只補差額,不重送

共享池的每筆有遞增序號,每個視窗記住自己讀到哪一號(SHARED_SEEN[pane])。 跑之前只帶入「序號大於它、且來自別的視窗」的部分。已經看過的永不重送,自己說的話也不會回灌給自己。

帶入時畫面會標示

該輪的視窗裡會出現一行 🔗 已帶入共享內容:N 則,來自 X、Y。 共享內容是自動帶入的,不是你手打的,所以它明確標記出來,不混進你的指令裡。

memory.md:同一份共享記憶,落成人看得懂的檔

每一輪的指令與產出,除了進共享池,也原文照錄寫進一個 markdown 檔。這是給人讀、給稽核用、也給視窗自己讀的。

# /Volumes/ADATA/dev/duo/memory.md(設了專案目錄就落在專案目錄)

# Code-Duo 共享記憶

四個視窗共用這一份。每一輪的指令與產出都自動寫進來,原文照錄,不摘要、不截斷。
檔案寫滿會自動接到 memory-2.md、memory-3.md;四個視窗都會被告知全部檔案。

## [5] PM+SA · 指令 · 2026-07-15 14:09:11

用一句話說明什麼是 append-only log。

## [6] PM+SA · 產出 · 2026-07-15 14:09:11

append-only log 是一種只允許在尾端新增紀錄、不允許修改或刪除既有紀錄的資料儲存方式。

寫滿了會自動接下一本

單檔上限 1 MB(純文字,要寫很久才會滿)。滿了就接 memory-2.md、memory-3.md, 舊檔不動、不覆蓋、不壓縮。帶入共享內容時會把「全部」的檔案路徑一起告訴視窗,不是只給最新那本, 所以任何一個視窗要翻更早的紀錄,都知道要讀哪幾個檔。

可稽核

curl -s http://127.0.0.1:8765/api/memory 列出目前所有記憶檔與各自大小。 檔案是純 markdown,直接 cat 或用編輯器開都行; 畫面上出現的路徑是藍色可點的,點下去直接在 Finder 定位。

實測:對 PM+SA 跑一輪後,memory.md 立刻出現該輪的指令與產出。 接著問 Audit(另一條獨立 session,從未被告知過任何路徑):「共享記憶檔的路徑是什麼?」 它答出 /Volumes/ADATA/dev/duo/memory.md。它只可能從自動帶入的共享段得知。

07b跨視窗接球

共享內容是被動的(所有視窗自然同步)。接球是主動的:把某個視窗的產出,當成一道指令交給另一個視窗去處理。

搭檔配對規則

partner(p) 找同一側的另一個視窗:

左半:w1 ↔ w2
右半:w3 ↔ w4

切成雙欄模式時,在當下可見的視窗之間重新配對。

三個觸發入口

手動:每則跑完的訊息底下長出 → Hand to X 與 → X review 兩顆鈕
自動:該窗標題列的 Response 開關打開後,它每跑完一輪就自動把產出交給搭檔審
指令:/review、/handoff

crossFeed(對面窗, 模式, 來源文字) 實際做的四件事

1. 取來源
lastOutput[來源窗],即該窗上一輪所有正文段落接起來的純文字
2. 蓋防迴圈章
reviewOnce.add(對面窗),標記「這一輪是被叫來審的」
3. 包成 prompt
角色指示 + --- partner output --- + 那段文字
4. 送出
streamRun(對面窗, prompt),從這裡起跟你手打一則指令給它完全同路
在 session 層面發生了什麼:那段文字會成為對面視窗自己 session 裡的一則新 user 訊息, 由對面視窗用它自己的 model / effort / cwd 去跑,續在它自己的 session 上。來源視窗的 session 完全沒有被觸碰。

防止無限互丟

A 跑完 ──(A 的 Response 開著)──> 丟給 B 審 ──> B 被蓋章 ──> B 跑完
                                                              │
                                          B 收尾時:          ▼
     wasReview = reviewOnce.delete(B)  →  true   # B 這輪是被叫來審的
     if (!wasReview && B 的 Response 開著) → 才會往外丟
                                              ↑ 條件不成立,鏈在此停住

效果:即使 A 與 B 兩邊的 Response 都開著,B 審完 A 之後也不會反手再叫 A 審。一次接球,一層而止。

11安全邊界

網路面

ThreadingHTTPServer(("127.0.0.1", 8765)) 只綁 loopback,不對外監聽,沒有反向代理、沒有雲端元件。 連線只有兩種:瀏覽器 → 本機 server;CLI → 各自原廠的服務(那是 CLI 自己的事,與 Code-Duo 無關)。

憑證面

不讀、不存、不傳任何金鑰。它呼叫 CLI 的方式,就是你在終端機自己打那一行的方式,沿用你既有的訂閱登入態。 Code-Duo 從未持有可用於認證的任何資料。

檔案寫入權限

由每個視窗自己的 mode 決定,原封不動傳給 CLI(Claude 的 --permission-mode、Codex 的 sandbox_mode)。 Code-Duo 不放寬也不收緊,權限模型完全是原廠 CLI 的。

資料落地

對話落在你本機的 ~/.claude 與 ~/.codex(CLI 自己寫)。 Code-Duo 自己的四個小檔落在 /Volumes/ADATA/dev/duo。沒有任何資料被送往第三方服務。

12Token 帳從哪來

畫面上的 token 數不是估的,是 CLI 自己報的。兩個引擎的取得時機不同。

引擎來源欄位時機與算法
Claude assistant · message.usage.output_tokens
result · usage.output_tokens		 每段輸出完成時累加;整輪結束時,用 result 事件的權威總量覆蓋修正
Codex turn.completed · usage.output_tokens
turn.completed · usage.reasoning_output_tokens		 每一輪結束時,把輸出與推理 token 相加後累計

另有一個獨立的用量面板,直接解析本機 session jsonl 統計成本 / 總 token / 快取命中率,與上面的即時計數是兩條路。
